# Modelling choices: from Hepatitis_std to an OWL knowledge base

This document records every decision taken when converting the relational
database into the ontology used for concept induction (Step 2 of the project
description). The ontology is generated by `src/build_ontology.py`; nothing in
`ontology/*.owl` is hand-edited.

## 1. Individuals and entity classes

| Table | OWL class | Individual IRI | Count |
|---|---|---|---:|
| `dispat` | `Patient` | `patient_<m_id>` | 500 |
| `Bio` | `BioProfile` | `bio_<b_id>` | 32 |
| `indis` | `LabRecord` | `lab_<in_id>` | 5,691 |
| `inf` | `DurationRecord` | `duration_<a_id>` | 196 |

`Bio` rows are called *profiles*, not biopsies: the standardised table
de-duplicates (fibrosis, activity) combinations, so one row is shared by up to
112 patients. The ontology keeps this sharing (one individual, many incoming
`hasBioProfile` links) instead of inventing one biopsy event per link.

## 2. Object properties (foreign keys / link tables)

| Link table | Object property | Domain → Range | Links | Cardinality |
|---|---|---|---:|---|
| `rel11` | `hasBioProfile` | Patient → BioProfile | 621 | 1..5 per patient, many-to-many |
| `rel12` | `hasLabRecord` | Patient → LabRecord | 5,691 | 0..105 per patient, one-to-many |
| `rel13` | `hasDurationRecord` | Patient → DurationRecord | 196 | 0..1 per patient |

No inverse properties are declared: concepts are learned for patients, and
DL-Learner's refinement operator would otherwise also explore the (useless)
record-to-patient direction.

## 3. Categorical values → classes and data properties

All attributes in Hepatitis_std are already discretised ordinal codes stored as
`varchar` (CTU: "numerical attributes were discretized and typed as varchar").
No further discretisation was needed. Each observed code becomes **both**:

* a value class, e.g. `GOT_3 ⊑ LabRecord`, `Age_5 ⊑ Patient`, `Fibrosis_4 ⊑ BioProfile`,
  `Duration_2 ⊑ DurationRecord` (69 value classes in total), asserted on the individual; and
* an integer data property, e.g. `gotCode = 3`, `ageCode = 5` (15 data properties),
  so that ordinal thresholds such as `zttCode ≥ 4` are expressible when the
  hypothesis language allows numeric datatype restrictions.

The clinical meaning and direction of the codes is not documented by the data
provider, so class names keep the original codes rather than labels like
"high". Interpretation in the report is therefore structural (which role, which
code) and ordinal (threshold direction), not clinical.

## 4. Target separation (no leakage)

`dispat.Type` is never written to any ontology. Labels live in
`data/processed/labels.csv`; the train/test split in `configs/folds/`. DL-Learner
only ever sees the training patients' IRIs as positive/negative examples.

## 5. Missing values and absent links

The database has no NULL values. Four patients have no lab record and 304 have
no duration record; these are simply absent links. Under the open-world
assumption an absent link is not a negative fact (see §7).

## 6. Ontology variants

| File | Flags | Purpose |
|---|---|---|
| `hepatitis.owl` (v1) | none | original KB, as built in the first phase |
| `hepatitis_v2.owl` | `--disjoint` | main KB for all experiments |
| `hepatitis_v2_noinf.owl` | `--disjoint --exclude-inf` | artefact ablation: `inf`/`rel13` removed |

`--disjoint` adds `AllDisjoint` axioms between the four entity classes and
between sibling value classes of the same attribute (16 axioms in v2). It does
not change what DL-Learner's closed-world reasoner computes, but it is required
for an OWL reasoner to entail negations such as `¬Sex_0` for a `Sex_1` patient
under the open-world assumption. Value classes of *different* attributes are
not disjoint (a patient is both `Sex_0` and `Age_5`).

`--closure` (available, not used in the final experiments) adds per-patient
role closure `hasX only {linked individuals}` / `hasX max 0`, which makes
universal restrictions entailed under OWA at the cost of a much heavier KB.

## 7. Closed-world vs open-world

DL-Learner is run with `reasoner.type = "closed world reasoner"`: the ABox is
materialised and `¬C`, `∀r.C` and cardinalities are evaluated as in a database.
The same concepts are re-evaluated with HermiT (`src/evaluate_concepts.py`) to
measure what is *entailed* under OWA with and without the disjointness axioms.
Everything reported as accuracy/F1 of a learned concept uses closed-world
semantics unless the table is explicitly labelled OWA.

## 8. Size

6,419 individuals, 73 classes, 3 object properties, 15 data properties, about
70k class assertions and 62k data-property assertions (7.7 MB RDF/XML).
DL-Learner loads and materialises it in about 3 s; Owlready2 in under 1 s.
